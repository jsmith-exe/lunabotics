# qpl_rover

ROS 2 package containing the core software, configuration, launch files, simulation assets, and localisation components for the QPL rover.

## Overview

`qpl_rover` brings together the main components required to run the rover in simulation and on the physical platform, including:

* Rover description and TF configuration
* Sensor and camera configuration
* Localisation
* Navigation-related configuration
* Simulation worlds and arena definitions
* Launch files
* Arena-specific configuration

The package is structured so that environment-specific and hardware-specific parameters can be changed through configuration without modifying the underlying nodes where possible.

qpl_rover/

### `config/`

Configuration for the rover and its operating environment.

Arena-specific configuration is stored under:

```text
config/arena/
```

while localisation-specific configuration is stored under:

```text
config/localisation/
```

The active arena can be selected through:

```text
config/arena/selector.yaml
```

### `launch/`

Launch files for starting individual components and complete rover subsystems.

### `qpl_rover/`

Python nodes belonging to the package.

### `worlds/`

Simulation environments for the supported arenas.

#### US arena terrain

`us_arena_terrain.world` (the `sim.launch.py` default) is the US arena with a sand floor (`worlds/arena_terrain/`) instead of the flat plane:

- **Gentle hills** for exercising the IMU: about ±7 cm, max slope 6°, mean ~2°. Every bump is rounder than 0.8 m radius, so the 0.15 m wheels never meet an edge.
- **Flat (z = 0)** in a 0.4 m band along the walls, in the starting zone, and in the construction/berm zone, blending into the hills over 1 m.
- **A single non-tiling regolith texture** covering the whole floor, so the visual odometry has features everywhere and no repeats to alias on. It is baked from a CC0 ambientCG photo (`arena_terrain/materials/source/`).
- **One mesh for both seeing and driving:** `arena_terrain/meshes/terrain.obj` is used as the visual *and* the collision, at the same pose, so the floor on camera is exactly the floor the wheels touch. There is no ground plane underneath it.
- **Sand compliance on the wheels (sim only):** the rover has no suspension, and on rigid ground Gazebo rocks it onto two diagonal wheels over any unevenness. Measured on these hills, skid-steer spin rate halved and wheel odometry over-reported the turn ~2x. So in simulation each wheel hangs from a short preloaded spring (`*_sand_joint`, 4000 N/m, ±3 cm, see `description/rover_core.xacro`), standing in for wheels sinking into sand. Ride height is unchanged and the real-rover URDF is identical. It adds 4 kg to the sim rover because ODE can't hold the chassis on near-massless spring links.
- The translucent zone-marker boxes from `us_arena.world` are left out because they would cut through the hills. Zones are shown in RViz.

Run `ros2 launch qpl_rover sim.launch.py world:=us_arena.world` for the old flat floor.

All terrain assets are generated by `worlds/generate_arena_terrain.py` and committed, so you only need to run it after changing it. Tunables are at the top of the script (`SEED`, `MAX_SLOPE_DEG`, `MAX_AMPLITUDE`, `OCTAVES`, `FLAT_ZONES`, texture settings).

```bash
python3 worlds/generate_arena_terrain.py   # prints height/slope stats
colcon build --packages-select qpl_rover
```

Notes:

- **Why not a Gazebo `<heightmap>`:** Gazebo Classic builds separate physics and render copies of a heightmap and places them differently (rendering ignores the model pose). It also only reads 8-bit images. The visible floor and the physical floor drifted apart, so the generator writes a plain mesh instead (5 cm vertex spacing, float heights).
- **Craters:** add `(x, y, diameter)` entries to `FEATURES["craters"]` and regenerate. They use arena coordinates, origin at the south-west corner. They are carved with smooth rims but are not slope-limited, so check the printed stats.
- **Boulders:** not implemented. They would be separate static models (mesh or sphere, visual = collision) placed at the terrain height in the world file. `FEATURES["boulders"]` is reserved for that.

## Localisation

The rover's localisation stack combines the available sensor sources to estimate the rover pose in the global `map` frame.

The package includes AprilTag-based visual localisation as part of this system.

### AprilTag Localisation

AprilTags provide an absolute visual reference for rover localisation. The `apriltag_observer` node detects tags from the rover's cameras, estimates the camera-to-tag pose, and uses the TF tree together with the configured arena geometry to calculate the rover pose.

The relevant configuration is split between:

```text
config/localisation/apriltag.yaml
config/arena/
```

This separates detector parameters, such as tag family and physical size, from arena-specific information such as tag placement and arena dimensions.

## Arena Configuration

Arena configuration is stored in:

```text
config/arena/
```

The configuration defines properties of the physical environment, including arena dimensions and AprilTag placement.

The active arena configuration is selected using:

```yaml
arena: us
```

in:

```text
config/arena/selector.yaml
```

### Arena and Simulation World Selection

**The arena configuration and simulation world are currently decoupled.**

`selector.yaml` determines which arena configuration is used by the localisation stack. It does **not** determine which simulation world is loaded.

When running in simulation, the arena must therefore be selected in two separate places:

| Purpose                            | File                         | Example                 |
| ---------------------------------- | ---------------------------- | ----------------------- |
| Localisation / arena configuration | `config/arena/selector.yaml` | `arena: us`             |
| Simulation world                   | `world:=` arg of `launch/sim.launch.py` | `us_arena_terrain.world` (default) |

These selections must be kept consistent. Changing only one can result in the localisation stack using the configuration for one arena while the simulator loads a different arena.

| Arena | `selector.yaml` | `sim.launch`     |
| ----- | --------------- | ---------------- |
| UK    | `arena: uk`     | `world:=uk_arena.world` |
| US    | `arena: us`     | `us_arena_terrain.world` (default), or `us_arena.world` for a flat floor |

Simulation worlds are stored under:

```text
worlds/
```

## Localisation Launch

The localisation system is launched through:

```text
launch/components/map_localisation.launch.py
```

This launch file brings together the relevant localisation components and loads the selected arena configuration.

The arena selected in `config/arena/selector.yaml` is used by the localisation stack, including the AprilTag localisation configuration.

`map_localisation.launch.py` does **not** select the simulation world. The simulation world is selected separately in `launch/sim.launch`.

## Obstacle Detection

Obstacles and walls come only from the two depth cameras. `launch/components/navigation_launch.py` starts one `depth_obstacle_filter` per camera alongside Nav2:

```text
/depth_camera_<front|rear>/depth/points
  -> depth_obstacle_filter_<front|rear>
  -> /depth_camera_<front|rear>/obstacles   (Nav2 marking)
     /depth_camera_<front|rear>/clearing    (Nav2 clearing, includes floor hits)
```

The filter measures each point's height above the floor under the rover, in `odom`, whose roll/pitch come from the IMU. A point is an obstacle if:

```text
height >= min_obstacle_height + range * height_slope_per_m     (0.16 m + 0.035 m per m)
```

The range term absorbs IMU tilt error, so floor far away isn't marked; walls are well above it at every range. Tune it in `config/depth_obstacle_filter.yaml`.

Both costmaps in `config/nav_params.yaml` use a 2D `ObstacleLayer` fed by those clouds, out to 4 m. The global costmap is a fixed map of the arena in `map`, so walls stay once seen.

Known limits: obstacles lower than the threshold (about 0.16 m close, 0.30 m at 4 m) are not marked, and the real camera mounts are taken from the URDF as level.

## Development Notes

When adding functionality to `qpl_rover`:

* Prefer configuration over hard-coded physical parameters.
* Keep arena-specific values in `config/arena/`.
* Keep component-specific parameters in the appropriate configuration directory.
* Use the existing TF tree for rover and sensor geometry where possible.
* Keep simulation environments consistent with their corresponding configuration.
* Avoid duplicating physical dimensions or transforms across nodes.

For component-specific documentation, additional README files can be added within the relevant subdirectory as the package grows.
